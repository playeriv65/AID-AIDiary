# AID Diary

- Talk to the user in Chinese. Code comments and docs are in English. Python uses uv.
- GPL-3.0 modification of Daily You: keep upstream copyright headers, LICENSE.txt and ADDITIONAL_TERMS.md, and keep the app clearly distinct from the official one (own name, own IDs, the modified-version notice in About). Nothing else in the app names Daily You; files and databases from Daily You (`daily_you.db`, `daily_you_*` backups and transfers) are still read so old data keeps working.
- Main branch is `main`. Larger tasks use a `task/<name>` branch in its own git worktree, merged back and removed when done. No remote is configured; do not publish or release unless asked.
- Develop natively on Windows: Flutter SDK `D:/software/flutter`, `PUB_CACHE=D:/software/pub-cache`, scripts via `scripts/dev.ps1`. Targets are Windows and Android only.
- UI reference is the Journey app (layout and features). Never copy its code, assets, illustrations or text; write prompts and copy ourselves.
- Data stays on the device. The only network use is OpenStreetMap map tiles, Nominatim (place names and place search), Overpass (nearby places in the location picker) and Open-Meteo weather; endpoints and settings live in `assets/config/app_config.json`, not in code. No AI, mem0 or cloud sync for now.
- `EntryStore.delete` moves an entry to Recently deleted; only `erase` removes it. Anything new that lists entries must skip sealed time capsules (`Entry.isSealed`) unless it shows them locked.
- In widget tests, change settings with `DiaryAppHarness.setSetting` (a real-time config write can lock the temp folder) and wait on SQLite work started by a widget with `DiaryAppHarness.pumpUntil`. When a tap itself changes config (enrolling in a coach program, answering its prompt), pump once and `EasyDebounce.cancel('save-config')` before settling: `pumpAndSettle` and `pumpUntil` move fake time past the 1 s debounce and start the write for real.
- Stories play as one chain (`StoryPlayer`, `TodayStory.open(from:)`): Today, the coach program's day, the throwback, then a closing card; a card over the app on wide windows, full screen on phones. Coach enrolment lives in config (`coachProgram`, `coachStartDate`, `coachAnsweredStep`); its daily notification follows the reminder pattern in `main.dart` (alarm plus localized text stored in SharedPreferences at startup).
- Feature ideas not built yet live in `TODO.md`.
- The UI follows Journey's Android tablet and phone layouts; Windows uses the tablet layout (no separate desktop layout).
- The app icon (flat, in the style of Google's app icons so it sits well among them) is drawn by `tool/icon/export_icon.py` (colours and scales at its top); it writes `assets/logo*.png` and `assets/logo.svg`, then `dart run icons_launcher:create` regenerates the Android launcher, round, adaptive, monochrome and notification icons and the Windows `.ico`. The Android 12+ splash uses the launcher icon.
- A new `Setting` must also go into `Settings.all`: startup prunes config keys missing from it (`test/config_settings_test.dart` checks).
- Videos and voice notes are attachments in the `entry_images` table and image folder, told apart by file extension (`MediaKind`), so backup and sync cover them unchanged.
- Build the APK with `./scripts/dev.ps1 apk` (flavors need `--flavor dev`). Test the home screen widget on the headless emulator; `am force-stop` cancels the widget's taps until it next updates, so use `am kill` for cold-start checks.
- Do not import data or keys from the old project, and do not delete the parent folder's `.private-legacy`.
- Verify UI without opening windows: widget tests, `./scripts/dev.ps1 screenshots`, and the Android emulator started with `-no-window`. Only launch the Windows app when the user wants to look at it.
- Day to day, develop and verify on Windows. Use the Android device (the user's Xiaomi Pad 7 over wireless adb, or the headless emulator) for plugin and native features, OEM behaviour, touch and IME, and profile-mode performance. Simulate a phone there with `wm size 1080x2400` and `wm density 420`, rotate with `cmd window user-rotation lock 0|1`, and restore all of them afterwards.
- The Dart and Flutter MCP server (Claude Code plugin `dart-flutter@dart-flutter`) is available. Prefer `analyze_files` and `lsp` for diagnostics and symbols, and `read_package_uris` / `rip_grep_packages` for dependency source. For live debugging on Windows run `./scripts/dev.ps1 windows-background` in the background: the window opens off screen and never takes focus (`AID_BACKGROUND_WINDOW`), the Flutter Driver extension is on, and the log prints the DTD URI; it uses the real Windows data folder, so back it up before a schema change and only read in driver sessions. On Android use `./scripts/dev.ps1 android -Device <id>` (same signing environment as `apk`). After editing `lib/**/*.dart` (not comments only), find the app with `dtd`, then `hot_reload`, or `hot_restart` when `initState`, `main` or static state changed. Check `get_runtime_errors`; drive and capture with `flutter_driver_command` (`tap` by ValueKey, `screenshot`). The `widget_inspector` tree is large (about 95k characters even as a summary), so search it rather than read it. On Android, screenshots can also use `adb exec-out screencap`.
- Tests are layered (`dart_test.yaml`): untagged files are unit tests (pure logic, no harness); `@Tags(['widget'])` for one page or component on `DiaryAppHarness`; `@Tags(['integration'])` for the whole app, real SQLite, migrations, isolates and archives. Keep pure tests out of widget files. While iterating, check with MCP `analyze_files` and run only the affected test files (per-file compilation dominates even the unit layer); run layers with `./scripts/dev.ps1 test-unit|test-widget|test-integration`, and everything once before committing with `./scripts/dev.ps1 test` (4 workers, so it does not pin every core).
- Before committing: `dart format`, `flutter analyze` clean, all tests passing, screenshots regenerated when the UI changed, README/SOURCE/AGENTS current.

# AID Diary

- Talk to the user in Chinese. Code comments and docs are in English. Python uses uv.
- GPL-3.0 modification of Daily You: keep upstream copyright headers, LICENSE.txt and ADDITIONAL_TERMS.md, and keep the app clearly distinct from the official one (own name, own IDs, the modified-version notice in About). Nothing else in the app names Daily You, and there is no compatibility with Daily You data or with older builds of this app (old file names, external-storage migrations, legacy password hashes).
- Main branch is `main`. Larger tasks use a `task/<name>` branch in its own git worktree, merged back and removed when done. The remote is the private GitHub repository `playeriv65/AID-AIDiary`; push `main` after committing. The old web app it used to hold is kept only as the tags `legacy-web` and `legacy-web-dev`. Do not publish a store release unless asked.
- Develop natively on Windows with `scripts/dev.ps1`, which reads this computer's toolchain paths from `scripts/dev.env` (ignored by git; template `scripts/dev.env.example`). Targets are Windows and Android only. `docs/SETUP.md` covers a new computer, the signing key, the test devices and how to reach them, and the outside resources (repository, keystore, Google Cloud project, sync server); `docs/DECISIONS.md` holds the owner's product decisions and the open questions; `docs/SYNC_NETWORK.md` records automatic paths, media budgets and the current network implementation. Read them before changing direction, and update them when the owner decides something. Run `./scripts/dev.ps1 pub` on a new checkout/worktree: it initializes dependencies for both the app and `cli/` before analysis or tests.
- UI references are other diary apps, mainly Journey (overall layout) and 一本日记 One Diary (the entry editor); their installers, screenshots and notes live outside the repository in `D:\program\diary-references\` (index in its README, one folder per app). Never copy their code, assets, illustrations or text; write prompts and copy ourselves. Get installers only from official stores on the user's devices, pulled with adb.
- Data stays on the device. The only network use is OpenStreetMap map tiles, Nominatim (place names and place search), Overpass (nearby places in the location picker) and Open-Meteo weather; endpoints and settings live in `assets/config/app_config.json`, not in code. Optional sync goes to the storage the user chose (their Google Drive, their WebDAV, or the AID sync server) and authenticated trusted devices, and is always end-to-end encrypted. No AI or mem0.
- `EntryStore.delete` moves an entry to Recently deleted; only `erase` removes it. Anything new that lists entries must skip sealed time capsules (`Entry.isSealed`) unless it shows them locked.
- An entry stores two things: `timeCreate`, when it was actually written, and `day` (`diary_date` column), the diary day it belongs to, which the writer may change at any time without touching `timeCreate`. Anything counted by day (grouping, "today", streaks, throwbacks, reviews, charts, reminders, widgets) uses `entry.day`, never the date of `timeCreate`. `DiaryDay` (`lib/utils/diary_day.dart`) only picks the default for new and imported entries from the settings `dayStartHour` / `dayAskUntilHour`; changing them must never move existing entries. `test/architecture/diary_day_rule_test.dart` fails on day math taken straight from `timeCreate`; show the clock time from `timeCreate` and the date from `entry.day`.
- In widget tests, change settings with `DiaryAppHarness.setSetting` (a real-time config write can lock the temp folder) and wait on SQLite work started by a widget with `DiaryAppHarness.pumpUntil`. When a tap itself changes config (enrolling in a coach program, answering its prompt), pump once and `EasyDebounce.cancel('save-config')` before settling: `pumpAndSettle` and `pumpUntil` move fake time past the 1 s debounce and start the write for real.
- Stories play as one chain (`StoryPlayer`, `TodayStory.open(from:)`): Today, the coach program's day, the throwback, then a closing card; a card over the app on wide windows, full screen on phones. Coach enrolment lives in config (`coachProgram`, `coachStartDate`, `coachAnsweredStep`); its daily notification follows the reminder pattern in `lib/background/background_work.dart` (alarm plus localized text stored in SharedPreferences at startup).
- Architecture follows Flutter's official app architecture guide as written down in `docs/ARCHITECTURE.md`: layers, folder roles, single sources of truth, when a screen gets a view model. `test/architecture/layer_boundaries_test.dart` enforces the dependency direction with no exception list; fix a dependency rather than working around the test, and update the doc when the architecture changes.
- Feature ideas not built yet live in `TODO.md`.
- Approved 2026-10-22 scope includes nearby migration/device authorization, network diagnostics, Scribble handwriting, independent appearance, local photo suggestions and Android streak/prompt/mood widgets. Finer mood context, goals/habits, question grids and the next performance pass are deferred. Appearance organization also references the installed Durian Diary; its code, assets and premium restrictions are not copied.
- All AID servers use the same implementation and parameters. Plan quotas require explicit `AID_SYNC_OPERATOR_LIMITS=true`; cache and relay share the configured UTC monthly media budget (default 1 GB). Self-hosting defaults to durable media with no plan quota, TTL or cache eviction; administrators may opt in. The official deployment enables those parameters. The client uses actual `operatorLimited` policy, never the domain or ownership, to choose limits and retention semantics.
- The UI follows Journey's Android tablet and phone layouts; Windows uses the tablet layout (no separate desktop layout).
- The app icon (flat, in the style of Google's app icons so it sits well among them) is drawn by `tool/icon/export_icon.py` (colours and scales at its top); it writes `assets/logo*.png` and `assets/logo.svg`, then `dart run icons_launcher:create` regenerates the Android launcher, round, adaptive, monochrome and notification icons and the Windows `.ico`. The Android 12+ splash uses the launcher icon.
- A new `Setting` must also go into `Settings.all`: startup prunes config keys missing from it (`test/config_settings_test.dart` checks).
- Videos and voice notes are attachments in the `entry_images` table and image folder, told apart by file extension (`MediaKind`), so backup and sync cover them unchanged.
- Sync (`lib/sync/`, `docs/SYNC_NETWORK.md`) keeps one encrypted format-4 space across shared storage and authenticated peers. `RoutedSyncBackend` requires a remote metadata acknowledgement; its SQLite ciphertext vault is an outbox, not an acknowledgement. Immutable gzipped packs (`packs/pack-*`, split past `sync.packKiB`) merge by item change time (`sync_items`); compaction snapshots include tombstones and cover old packs, which are removed from a remote path only after that path acknowledges the replacement snapshot. Media follows metadata through persistent SQLite tasks and 1 MiB AEAD chunks/manifests, reusing ciphertext across retries and path changes. Never couple item versions or task identity to a transport. LAN is available across storage backends; public direct discovery, WebRTC/STUN and bounded live relay require an AID-compatible WebDAV account and `/api/sync/network`. `InternetTransport` authenticates fresh server sessions plus client-generated nonces with MK-derived AEAD hello/echo/ready; directory presence never grants trust. Public endpoints need a signed MK/device probe; ICE and relay use session-bound `PeerObjectLink` RPC. No TURN. A WebSocket outage closes relay while established public/ICE links may continue; route IDs must fence session generations. Operator-cache and live-relay allowances are separate from each other, direct and personal-storage traffic; a direct writer pool must never silently select relay. Cache or relay receipt is not proof of a durable backup. Format 3 and earlier fail explicitly: never automatically reset a remote space or delete the local diary to fix that error; a live remote reset needs the owner's approval. The AID sync server under `server/` is Go + SQLite (its README owns policy settings). Production server source `887dd27` and nginx WebSocket headers were deployed on 2026-10-22; deployment acceptance and physical network evidence are separate facts. Google Drive uses `GoogleDriveBackend`, `drive.file` scope and `GoogleAuth` (`docs/GOOGLE_DRIVE.md`). `./scripts/dev.ps1 test-server` runs server tests; live app tests use `flutter test --tags live` with `AID_SYNC_URL`, `AID_SYNC_USER`, `AID_SYNC_PASSWORD`, or `AID_GOOGLE_LIVE` for Google Drive. Use local/scratch targets unless live changes are explicitly authorized.
- Build the APK with `./scripts/dev.ps1 apk` (flavors need `--flavor dev`; the dev flavor is the package `dev.aid.diary.beta`, never `.dev`, see `docs/REFRESH_RATE.md`). Debug and profile builds are signed with the release key whenever `android/key.properties` exists, so any build installs over any other: HyperOS asks on the device before every new install (and a key change forces one), so never uninstall a development app or change its key without asking. `flutter drive` uninstalls the app when it finishes unless given `--keep-app-running`. `./scripts/dev.ps1 release` builds the `independent` flavor (`dev.aid.diary`, the user's everyday app on their phone and tablet) and installs it with `adb install -r` on every connected device. It is signed by `android/key.properties`, which is ignored by git and only exists in the main checkout; the keystore lives in `D:\software\keys`. Do not uninstall it or clear its data without asking. Test the home screen widget on the headless emulator; `am force-stop` cancels the widget's taps until it next updates, so use `am kill` for cold-start checks.
- Do not import data or keys from the old project. Its uploaded files sit outside the repository in `D:\program\AID-AIDiary-legacy`; do not delete them.
- The app is agent-native (`docs/ARCHITECTURE.md`): every feature is an action in `lib/actions/`, which the GUI's buttons and command palette and the `aid` CLI (`cli/`, built with `./scripts/dev.ps1 cli` to `build/cli/aid.exe`, tested with `test-cli`) all run. A new feature starts as an action. To check the app on a device, drive it with `aid` rather than taps and screenshots: `aid -d <adb serial> app.status`, `aid -d <serial> entry.seed count=4000`, `aid -d <serial> sync.now`; `aid guide` lists every action. Over adb `aid` reaches the dev flavor (it reads the token with `run-as`) and starts it when needed; development builds always serve the API, other builds only with Settings → Command line turned on.
- Touch feedback goes through `widgets/haptics.dart` (selection for tabs, switches and moods; success, warning and error for outcomes and destructive prompts), sparingly, only from the GUI.
- Verify UI without opening windows: widget tests, `./scripts/dev.ps1 screenshots`, and the Android emulator started with `-no-window`. Only launch the Windows app when the user wants to look at it.
- Day to day, develop and verify on Windows. Use the Android device (the user's Xiaomi Pad 7, the test device, over adb in TCP mode on port 5555 so the address stays fixed; or the headless emulator) for plugin and native features, OEM behaviour, touch and IME, and profile-mode performance. The user's phone is for their own use: test there only when asked.
- Sync and pairing without a phone or a cloud account: run the AID server from `server/` on this computer (`go run ./cmd/aid-sync adduser NAME`, then `serve`) and start several hidden Windows copies of the app, each with its own `AID_DATA_DIR` and `AID_API_INFO` (secrets and preferences go to files there, not to the platform stores), then drive them with `aid`: `sync.connect_webdav`, `sync.pair_offer` on one and `sync.pair_accept` on another. A phone or tablet reaches the server through `adb reverse tcp:PORT tcp:PORT`; debug and profile builds allow plain HTTP to 127.0.0.1 for this.
- Physical network checks use isolated data: Android dev launches may set `aid_test_workspace` to an ASCII name of 1 to 64 letters/digits/`_`/`-`, which places every store, including secrets, under `files/network-tests/<name>`; regular app data is untouched. Copy that workspace's API info privately and forward its port for CLI access (`docs/SETUP.md`); do not assume `aid -d` reads the scratch API file. `sync.network_paths paths=lan,direct,ice,relay,cache` is development-only; omit paths to isolate a check, optionally set `stunOnly=true` to exchange only `srflx`/`prflx` ICE candidates, and restart to restore defaults. `sync.network` candidate-pair stats, attachment hashes and actual path evidence are required before claiming a physical route passed. Temporary authorized public test endpoints use separate data and are removed after the check; they are not a production deployment.
- Windows network tests reuse one permanent executable path: configure `DEV_WINDOWS_RUNTIME`, build with `windows-build`, then copy the existing bundle with `windows-stage`. Staging holds checkout/destination locks, refuses a running or unsafe destination, and neither launches nor changes firewall policy. Keep scratch data elsewhere. Win32 firewall application grants are tied to the full executable path, not the Android package; obtain initial consent for the fixed path and reuse it across worktrees instead of repeatedly authorizing new build paths. Current validation continued from its already authorized fixed runtime; retargeting existing rules failed with non-admin AccessDenied and changed nothing. Android scratch launches must not schedule/cancel regular Workmanager tasks. Same-Wi-Fi global IPv6 or gathered STUN candidates do not prove cross-WAN connectivity; inspect the nominated pair and keep the verification limits in `docs/SYNC_NETWORK.md` current.
- `sync.network_reconnect delaySeconds=1..60` (default 5) is development-only: disconnect signaling while preserving established direct links, then reconnect after the delay. A remote directory `leave` or empty peer list must not close an authenticated working direct connection. Windows/Pad checks verified ICE text and fresh hash-matched media with one-sided signaling loss and with the isolated test server stopped; this remains same-Wi-Fi evidence. Later checks verified cloud-off nearby migration, Android hardware-key authorization/rotation/revocation, policy changes on one endpoint, and 17 MiB storage-only media with limits off. The final Flutter suite passed 789 tests with six external-service tests skipped (`docs/SYNC_NETWORK.md`). Production source `887dd27` and nginx WebSocket headers are deployed with operator limits explicitly enabled at 1 GB per UTC month; public deployment acceptance passed and the temporary account was removed. Different-NAT validation remains deferred; do not add an Osaka relay for it.
- Frame rate is a requirement: every scenario must keep the display's refresh rate. Debug first (hot reload, Windows), then measure in profile mode with `./scripts/dev.ps1 frame-rate -Device <adb serial>|windows` (`scripts/frame_rate.ps1`, scenarios and limits in `scripts/frame_rate.json`). On a phone or tablet it measures the installed app, so install a profile build first with `./scripts/dev.ps1 profile -Device <adb serial>` (it stays usable by hand); on Windows it builds one with `AID_DEV_BUILD` and runs it in the hidden window on scratch data (`AID_DATA_DIR`). It seeds 4000 entries with 400 photos, opens places with `aid ui.navigate`, flings with `adb input swipe` or `aid ui.fling`, and counts frames with `aid perf.start`/`perf.stop` (build and raster times, frames over budget, skipped refreshes) and on Android also SurfaceFlinger timestats (what reached the screen). It fails above 1% and leaves the numbers in `build/frame_rate.json`, each scenario's timeline in `build/frame_rate_timeline/<scenario>.json` and a pass with every widget build, layout and paint in `build/frame_rate_timeline/widgets.json` (the app starts with an endless timeline buffer) (`aid trace start|stop`; open them in ui.perfetto.dev). On Xiaomi devices first check the app is not held at 60 Hz as a game (`docs/REFRESH_RATE.md`). Simulate a phone there with `wm size 1080x2400` and `wm density 420`, rotate with `cmd window user-rotation lock 0|1`, and restore all of them afterwards.
- The Dart and Flutter MCP server (Claude Code plugin `dart-flutter@dart-flutter`) is available. Prefer `analyze_files` and `lsp` for diagnostics and symbols, and `read_package_uris` / `rip_grep_packages` for dependency source. For live debugging on Windows run `./scripts/dev.ps1 windows-background` in the background: the window (`AID_BACKGROUND_WINDOW`) sits on screen below other windows but is nearly transparent, click-through, off the taskbar and never focused (an off-screen window gets no vsync, so route animations never finish), the Flutter Driver extension is on, and the log prints the DTD URI; it uses the real Windows data folder, so back it up before a schema change and only read in driver sessions. On Android use `./scripts/dev.ps1 android -Device <id>` (same signing environment as `apk`). After editing `lib/**/*.dart` (not comments only), find the app with `dtd`, then `hot_reload`, or `hot_restart` when `initState`, `main` or static state changed. Check `get_runtime_errors`; drive and capture with `flutter_driver_command` (`tap` by ValueKey, `screenshot`); turn `set_frame_sync` off while a text field has focus, since its blinking cursor keeps frames pending. The `widget_inspector` tree is large (about 95k characters even as a summary), so search it rather than read it. On Android, screenshots can also use `adb exec-out screencap`.
- Tests are layered (`dart_test.yaml`): untagged files are unit tests (pure logic, no harness); `@Tags(['widget'])` for one page or component on `DiaryAppHarness`; `@Tags(['integration'])` for the whole app, real SQLite, migrations, isolates and archives. Keep pure tests out of widget files. While iterating, check with MCP `analyze_files` and run only the affected test files (per-file compilation dominates even the unit layer); run layers with `./scripts/dev.ps1 test-unit|test-widget|test-integration`, and everything once before committing with `./scripts/dev.ps1 test` (4 workers, so it does not pin every core).
- Every page stays alive and rebuilds on each diary change, so keep per-entry work out of build loops: use the store's indexes (`EntryStore.getEntriesForDate`, `EntryImagesProvider.getForEntry`, `TagsProvider.getEntryTagsForEntry`) and cache by list identity (lists are replaced on change). A local `DateTime` costs a time zone lookup (about 20 µs on Windows): use `Entry.day` for an entry's date and `parseLocalTime` for stored times. Check a change against a seeded diary of several thousand entries.
- When something behaves oddly, search the web first (issues and forums, in English and Chinese for Chinese ROMs) before guessing or running many local experiments.
- When the owner asks to remove something, delete the code and its tests; do not add tests, checks or doc lines that guard against it coming back. Tests check the behaviour that remains.
- A differential check against a reference implementation runs once: generate, compare, fix, then delete the harness and its fixtures (keep them in a scratch folder, not the repository).
- Before committing: `dart format`, `flutter analyze` clean, all tests passing, screenshots regenerated when the UI changed, README/SOURCE/AGENTS and docs/ARCHITECTURE.md current.
- Native Flutter builds and runs in one checkout must use `scripts/dev.ps1`: its file lock prevents Windows and Android from racing over Flutter's shared asset staging directory. `windows-build` builds without opening a window. Use another worktree for concurrent platform builds; multiple already-built binaries may run on separate scratch data directories.
